# 钢琴档案压缩位图索引

几十万台钢琴档案（品牌 / 型号 / 门店 / 租赁状态 / 上次调律月份 / 音板是否开裂 / 琴龄）
用一个压缩位图索引支撑客服的 6–9 条件组合筛选。每条查询都变成位图之间的交、并、差、
异或运算，并附带一个页面展示条件查询、每张位图的容器构成、各类运算耗时和索引内存。

## 运行

```bash
go run ./cmd/server -n 300000            # http://127.0.0.1:8080
go run ./cmd/bench  -n 300000 -q 3000    # 随机查询 + 暴力集合对拍 + 耗时统计
go test ./...                            # 单元/对拍测试
```

## 结构

```
internal/bitmap    压缩位图：分桶、三种容器、两两运算、整段范围操作、快统计、序列化/mmap
internal/bitslice  数值字段的按位切片，范围条件用逐位比较
internal/idx       钢琴索引：字段取值位图、bit-slice 列、查询求值、增量增删改
internal/query     查询语法（& | ! 括号，in / between / 比较）
internal/web       页面与 JSON API（查询、位图结构、容器构成、内存、范围操作、增删）
cmd/server|bench   服务与压测入口
```

## 设计要点

**分桶 + 三种容器。** 行号按高 16 位分桶，每桶 65536 个低位值对应一个容器：

- `array`：有序 `[]uint16`，稀疏时最省（≤ 4096 个值）；
- `bitset`：固定 1024 个 `uint64`（8 KiB），稠密时摊销成本最低；
- `run`：`[start,end]` 区间数组，连续段多时（例如 `all` 或某些门店）只有几十字节。

容器类型由 `chooseKind(card, runs)` 按“实际占用字节最小”选择，增删和运算结果都会在
三种类型之间自动转换（数组超过 4096 个值 → 位图；位图删到 4096 以下 → 数组；游程数
超过 1024 → 位图）。位图的 `card` 增量维护，基数、rank、select、range-card 都不展开
位图：`Rank` 用 popcount 前缀扫描，`Select` 用 `(w & (w-1))` 逐位跳，`RangeCard` 是两次
`Rank` 的差。

**两两运算。** `opAnd/opOr/opXor/opAndNot` 对 3×3 种容器组合各有一个专门实现：
数组×数组走双指针，位图×位图走 1024 次机器字运算，游程×游程走区间归并，
混合组合按较稀疏的一方迭代/扫桶。结果容器类型只由结果的基数和游程数决定。

**整段范围操作。** `Bitmap.SetRange/FlipRange` 只遍历范围覆盖到的桶，首尾桶做掩码，
中间整桶直接整体置位/清零/取反；范围外的桶连指针都不变（测试断言指针同一性）。

**数值范围。** `age`、`tuned`（自 2014-01 起的月份，`never` 单独一张位图）用 bit-slice：
每个 bit 一张位图，`>=`/`<=`/`between` 从最高位往下用位图运算逐位比较，无需逐行扫描。
求值时把平面转成“每桶固定 1024 字”的临时格式，中间结果不再反复选容器类型，
表达式结束时一次性压缩回三种容器。

**序列化 / mmap。** `Bitmap.Serialize` 写出版本头、桶键、容器偏移与长度、容器种类、
8 字节对齐的容器负载；`OpenMapped` 直接 `mmap` 并让容器指向映射内存，不反序列化即可
做交并差、rank/select。`bitslice.SaveColumn` 把整列平面写成一组可映射文件。

**查询语法。** `&` 与、`|` 或、`!` 非、括号；`field = v`、`!=`、`in (...)`、
`age between 20 .. 40`、`tuned < 2022-01`、`tuned = never`、`crack = true`。
`!` 以“当前存活的全部行”为全集：删行会同时从 `All` 和所有字段位图中移除，
因此被删除的行不会从 `!cond` 里漏回来。行增删改都做增量更新：单值改走
`applyAdd/applyRemove`，数值更新只翻转变化的 bit 平面。

## 验证

`go test ./...` 覆盖：

- 3×3 容器组合 × 4 种运算 × 多种数据形态，与 `map[uint16]struct{}` 暴力结果完全相同；
- 数组↔位图、游程↔位图的阈值边界（4096/4097、游程阈值）单独测试；
- 随机单点增删 4000 次，每步与集合对拍并检查容器不变量；
- 整段置位/清零/取反与逐行比较一致，且范围外的桶未被改写；
- 所有数值范围条件与逐行比较一致（含 `never`、月份字面量、开闭区间）；
- 3000 条随机 6–9 条件查询与逐行暴力求值逐行完全相同；
- 增量增删改后所有字段位图、数值平面与记录一致；删除后 `!` 不包含死行；
- mmap 打开的位图与内存位图基数、rank/select、交并结果一致；
- Web API 端到端（查询、位图结构、容器构成、内存、范围操作、增删改）。

`cmd/bench` 在 30 万条档案上跑 3000 条随机查询，输出 p50/p90/p99、耗时分布，并与暴力
实现逐条比对：

```
all 3000 queries match the brute-force reference
latency: p50=0.35ms p90=0.60ms p99=1.09ms max=1.68ms   (30 万档案，6–9 条件)
```

AND 的操作数按基数从小到大求值，`!` 的结果直接以位图形式补齐（不做展开），
稠密结果的容器选择会先数游程、只有游程确实更省时才转成 run 容器。
